# DocFusion

[English](README.md) | **简体中文**

[![CI](https://github.com/wwkkyy0325/DocFusion/actions/workflows/ci.yml/badge.svg)](https://github.com/wwkkyy0325/DocFusion/actions/workflows/ci.yml)

**把 PDF、图片和 Office 文档变成结构化 Markdown —— 全在本地，只做一次，落到一个你本来就会用的文件树上。**

DocFusion 是一个本地优先的文档摄取流水线，用 Rust 写成。它读进一个文档，自己判断该用哪个引擎来读，把结果写成带出处信息的 Markdown，并建立索引，保证同一件事不做第二遍。一套内核，两个出口：一个为 agent 设计的命令行，和一个用来转换、审阅单个文档的桌面窗口。

没有服务端，没有账号，没有向量库。产物就是文件。

```
                 ┌──────────────────────────────────────────────┐
   一个文档 ────▶│ 嗅探 mime → BLAKE3 → 见过没有？              │
                 └──────────────────────────────────────────────┘
                        │ 没见过
                        ▼
   有文字层的 PDF ──▶ PDFium        （确定性，不用模型）
   扫描件 / 图片 ──▶ OCR + 版面     （本地，ONNX Runtime）
   docx/xlsx/pptx ─▶ 纯 Rust 解析器
                        │
                        ▼
              块结构 IR（文本 + 坐标 + 置信度 + 引擎）
                        │
                        ▼
        校验（可选的第二引擎，分歧原样保留）
                        │
                        ▼
     Markdown + YAML 前言 + 图片资源 → 原子写
```

## 它是什么

大多数文档流水线回答的是*"我怎么从 PDF 里把文字弄出来？"*。DocFusion 回答的是一个更窄也更难的问题：**我怎么把一个文档放进档案里、以后还能找回来，并且从不对它说了什么撒谎？**

这个提法决定了所有功能：

| | |
|---|---|
| **按内容寻址** | 每个文档都用它字节的 BLAKE3 哈希作为身份。同一个文件从三个目录进来，只存一份，但知道三个名字。 |
| **块结构 IR，不是字符串** | 抽取产出的是 `Vec<Block>`，每个块带坐标、置信度和产生它的引擎。面对一个字符串，两个引擎无法比较，分歧也无法定位。 |
| **校验是一等步骤** | 当某处读得不确信 —— 或者文中出现金额、日期、编号 —— 就会去问第二个引擎。分歧会记进文档，而不是被抹平。 |
| **知识库就是普通 Markdown** | `docs/` 就是一个装着 `.md` 的普通目录，带 YAML 前言。Obsidian 能打开，`git` 能版本管理，agent 能直接 `grep`。不存在需要逃离的锁定。 |
| **不需要你选模型** | 本地 OCR 用一套固定且按摘要锁定的权重。视觉模型是可选的，而且是你自己的 —— 任何 OpenAI 兼容端点，本地或云端都行。 |

### 它不做什么

明确的非目标，写下来是为了不让它们悄悄长出来：

- **永远不做向量检索，不做重排。** 搜索就是对一个 SQLite 文件的一条 SQL 查询（FTS5），并且应该一直是这样。摘要、实体抽取、自动打标、关系图、双链，都是**另一个产品**，它会消费本项目的产物 —— 产物是纯 Markdown，正是为了让那件事在别处好做。
- **不做多用户、不做服务端、不做鉴权、不做配额。**
- **不读老版 Office 格式**（`.doc`、`.xls`、`.ppt`）—— 识别出来并给出转换提示，而不是读一半。
- **手写 OCR 不是一等目标。**

这样换来的优先级是可度量的：**一个文档多快进去，多快出来。**

## 三条原则

三条真正约束着代码的规矩，每一条都被打破过一次，也都被抓了回来：

1. **同样的字节绝不处理两次。** 缓存命中由内容决定，外加产生这份读法的引擎、模型和提示词版本 —— 所以引擎变了会重读，其他情况不会。
2. **绝不无声地撒谎。** 读得不确信的地方会说明。两个引擎之间的冲突会写进文档。支撑不了的结论会报成问题，而不是报成一次空的成功。
3. **绝不让用户去猜。** 拼错的配置项是带文件名和行号的错误，不是被默默忽略的键。`docfusion schema` 把整套契约 —— 命令、字段、退出码 —— 都公布出来，agent 不需要去解析帮助文本。

## 快速开始

需要一个 Rust 工具链。**版本钉在 `rust-toolchain.toml` 里**，所以 `rustup` 会在你第一次跑 `cargo` 时自己装上，不需要你选 —— 依赖要求的下限是 1.88，但真正用来构建和检查的是钉住的那个版本，因为让一个你写代码时并不针对的编译器来检验它，没什么意义。（如果身处只镜像 channel、不镜像具体版本的镜像站，这次安装会 404；文件里写了怎么从上游取一次。）

```bash
git clone https://github.com/wwkkyy0325/DocFusion.git
cd DocFusion
cargo build --release
```

产物是 `target/release/docfusion`。

```bash
# 放一个文档进去。有文字层的 PDF 不需要任何别的东西。
docfusion --root kb add report.pdf

# 看它变成了什么。
docfusion --root kb show report.pdf

# 或者当文件读。
cat kb/docs/report.md
```

第一次 `add` 扫描件或图片时，会去取识别权重 —— 7 MB，一次，先校验 SHA-256 才敢用。启动时不下载任何东西，后台也不刷新。

```bash
docfusion doctor        # 这个安装能读什么，还缺什么
```

想点鼠标的话，直接开窗口：

```bash
cargo run --release -p docfusion-gui
```

## 命令行

```
docfusion add <paths...>            处理并入库
docfusion show <id|path>            把 Markdown 打到标准输出
docfusion list [--status S]         列出文档
docfusion export <id> --to <fmt>    把文档、或其中一个块，写成文件
docfusion search <words...>         按内容找文档
docfusion index                     从 Markdown 重建搜索索引
docfusion reindex [id|path]         用现在这台机器上的引擎重读
docfusion forget <id|path>          从索引里摘掉；Markdown 留着
docfusion delete <id|path>          删掉它、它的 Markdown 和它的副本
docfusion reconcile [--fix]         拿文件树修索引
docfusion bench --set <dir>         用参照语料给引擎打分
docfusion doctor                    能读什么，还缺什么
docfusion schema                    把输出契约作为 JSON 公布出来
```

指名一个文档可以用它的内容 id、id 的前几个字符、源路径，或者文件名 —— 手边有哪个用哪个。

### 为被程序调用而设计

agent 拿到的是完整功能，四条规矩让这件事是安全的：

1. **`--json` 把 NDJSON 打到标准输出，所有日志走标准错误。** 日志污染标准输出是 agent 集成最常见的翻车方式。
2. **退出码是有含义的：** `0` 成功 · `1` 出错 · `2` 部分失败 · `3` 没有文字层，必须指定引擎 · `4` 索引不一致，跑 `reconcile`。
3. **`docfusion schema` 是自描述的**，不需要从帮助文本里猜。
4. **每个会改动的命令都支持 `--dry-run`。**

配置可以完全用命令行参数或环境变量给出（`DOCFUSION_ROOT`、`DOCFUSION_ENDPOINT`、`DOCFUSION_MODEL`、`DOCFUSION_API_KEY`、`DOCFUSION_VERIFY` 等），所以 agent 永远不需要读某个文件才知道工具是怎么配的。

## 配置

一个文件，按用户存，**在任何仓库之外** —— 它装着 API key，而一个放在文档旁边的文件，是迟早会被提交上去的文件：

```
%LOCALAPPDATA%\DocFusion\config.toml      Windows
$HOME/.cache/docfusion/config.toml        unix
```

```toml
endpoint = "https://api.deepseek.com"
model    = "deepseek-flash"
api_key  = "sk-..."
```

**优先级：命令行参数 → 环境变量 → 配置文件 → 内置默认值。**

视觉端点完全是可选的。一个都不配，DocFusion 照样读所有文字层 PDF、所有 Office 文件，以及所有扫描件（走本地 OCR）—— 端点买到的是**结构**（标题、表格、跨栏的阅读顺序），不是"能不能读"。

任何实现了 `POST {base_url}/v1/chat/completions`、并且图片能放在 `user` 消息里的端点都能用：`llama-server`、Ollama、LM Studio、vLLM，或者云端 API。一个客户端覆盖全部。窗口的设置页有个**测试**按钮，它会画一张带数字的页面给端点看，然后告诉你那个数字有没有回来 —— 因为地址能应答，跟模型能看见，不是一回事。

## 一个文档是怎么被读的

**路由靠内容，不靠扩展名**，而第一条规矩是：**有文字层的 PDF 绝不碰模型。** 那条路径是确定性的、瞬间的、免费的；交给识别模型只会更慢，而且更不准。

| 输入 | 走的路径 |
|---|---|
| 有文字层的 PDF | PDFium。不用模型，不联网，不花钱。 |
| 扫描版 PDF、图片、扫描件 | 本地 OCR，装了版面模型还会加上它 |
| DOCX、XLSX、PPTX、TXT、MD | 纯 Rust 解析器，直接进 IR |

### 校验

只在值得问的时候才问第二个引擎 —— 策略有 `doubt`（第一个引擎没把握的地方，或者读到需要精确的值）、`fields`（只在文中出现金额、日期、编号时）、`always` 和 `off`。

两者不一致时，**分歧会被保留**：文档里带着这份读法、第二个意见，以及它们不一致的页码，让人来判断。自动裁决等于把一个猜测当作答案端上来。

## 知识库在磁盘上的样子

```
knowledge/
  docs/
    2024-annual-report.md         # YAML 前言 + 正文
    _assets/
      a3f9c2.png                  # 抽出来的图，按内容寻址
  .docfusion/
    manifest.db                   # SQLite 清单 + FTS5 索引
    sources/
      a3f9c2….pdf                 # 读过的那些字节的一个副本
    cache/                        # 引擎结果缓存
```

**去重按内容。** 同样的字节、同样的引擎、同样的模型、同样的提示词版本 ⇒ 缓存命中，第二个路径会被记成第一个的别名，而不是第二个文档。

**`.docfusion/sources/` 留了一份读过的全部内容**，理由不是"出处"，而是：*原件一旦挪走，那个文档就永远读不了了* —— 而 `reindex` 存在的意义就是在引擎或模型变了之后重读文档，它需要那些字节。把这些副本放在 `.docfusion/` 而不是 `docs/` 旁边是刻意的：一个会被同步、会被提交的 `docs/`，不该把读进去的合同和银行流水跟着 Markdown 一起拖出去。

代价是磁盘 —— 知识库现在跟放进去的东西差不多大。`docfusion delete` 是让某个东西不再占地方的办法；`forget` 是可逆的那一半，并且刻意不释放空间。

**写入是原子的**（临时文件 + Windows 上的 `ReplaceFileW`/`MoveFileExW`），当下面有什么东西挪过位置，`reconcile` 会拿文件树把索引修回来。

## 搜索，以及中文

搜索就是 SQLite FTS5，上面什么都没有 —— 没有向量，没有重排。

**FTS5 没有中文分词器，所以文本在存进去之前先分好词：一个字一个 token。** 这是对中文语料影响最大的一个决定，而它是量出来的，不是偏好。用默认分词时，一整句中文在 FTS5 眼里都是"字母数字"，会变成一整个 token，于是 `合同` 什么都匹配不到。一个字一个 token 让每个字都可被寻址，而一个两字词就变成两个相邻的 token，短语查询就能找到。

那个显而易见的替代方案 —— FTS5 的 `trigram` 分词器，号称什么文字都能处理 —— 是被量过之后否掉的：它会对短于三个字符的查询静默失效，而那就是大多数两字中文词。按字分词还**更小**，不是更大。

查询在内部会被加引号，所以 `合同` 是在要 `合` 和 `同` 这两个相邻的 token，而不是要两个独立的字。

## 桌面应用

盖在同一套内核上的一个 Tauri v2 窗口。前端是手写的 HTML/CSS/JS，原样服务 —— **构建里没有任何 Node 或 npm 步骤**；`cargo build` 就是全部构建，Markdown 到 HTML 的转换在 Rust 里做。唯一一个内嵌的依赖（CodeMirror 6，MIT）是以单个 ES 模块提交进仓库的，因为内容安全策略是 `default-src 'self'`，而一台离线的机器也必须能用。

三个页签：

| 页签 | 做什么 |
|---|---|
| **文档** | 转换一个文件、读结果、审阅引擎之间的冲突，然后复制或导出 |
| **记录** | 库里的一切：浏览、搜索、打开、忘掉、删除 |
| **设置** | 模型与端点、主题，以及本地模型集的状态 |

文档页上：

- **块是可寻址的。** 鼠标悬停会把那个块洗一下，一个 `⋯` 按钮打开它的操作 —— 复制，或者单独导出这一块。块的编号跟导出取用的顺序一致，所以"第 7 块"在窗口里和在命令行里是同一个意思。
- **Markdown 可以就地编辑**，渲染结果摆在旁边，编辑会带着自己的时间戳写回文档，这样一份被编辑过的文档永远不会被误当成引擎的读法。
- **原文可以摆在读法旁边看。** 对 PDF 或图片，左半边显示被读的那一页；对没有页的文件，它会说明这一点，而不是留半个空面板 —— Markdown 唯一没法告诉别人的，就是它当时在看什么。

## 导出

规矩是：**一次导出要保留光有文字保不住的东西。**

| 格式 | 用来干什么 |
|---|---|
| `md` | 文档存下来的原样 |
| `html` | 保留强调和标题层级的一个页面 |
| `txt` | 文字，只对整篇文档（单个块的文字是 `show` 和复制按钮的事） |
| `docx` | 一个 Word 文件 —— 真的 WordprocessingML 文档，从解析后的 Markdown 生成 |
| `xlsx` | 一个表格文件，一张表一个 sheet |
| `csv` | 单独一张表的行 |

`docx` 和 `xlsx` 是 zip，所以必须给 `--out`；这两个都没法打到终端上。格式之间的差别正是重点：同一张表导出成 CSV 和导出成 Markdown，对"这是个什么东西"的回答是不一样的。

## 引擎与模型

| 关注点 | 选择 |
|---|---|
| PDF 文字层与渲染 | **PDFium**（Chromium 的引擎），嵌在二进制里。中文安全。 |
| 本地 OCR | **RapidOCR** —— PP-OCRv6 tiny 的检测、识别、方向分类器 —— 跑在 **ONNX Runtime** 上 |
| 页面结构 | **PP-DocLayout_plus-L** —— 找标题、表格、页眉页脚、公式 |
| 视觉 | **用户自己的端点。** 不是我们该跑的。 |
| DOCX/XLSX | `zip` + XML，`calamine` |
| Markdown → HTML | `comrak`（GFM） |
| 存储 | SQLite（`rusqlite`，内置）加 FTS5 |
| HTTP | `ureq` —— 阻塞式、体积小；流水线本身是同步的，上异步运行时等于白白负重 |

**模型集是六个文件、144 MB，一个都不在二进制里。** 这是一次取舍，代价值得直说：全新安装的 DocFusion，在权重到达之前读不了任何图片和扫描版 PDF。换来的是一个唯一定义"完整"意味着什么的地方、先验证摘要再相信任何东西、可断点续传的下载、以及按顺序尝试的多个镜像。没人要，就什么都不取。

这几部分并不等价，这个划分是刻意的：**识别集是 6.9 MB，不可省略** —— 没有它，一页本来是图片的文字根本读不了。**表格模型是 7.8 MB**，**版面模型是 124 MB**，两者都是改进而不是能力：这个工具读过的每一页，都是在没有它们的情况下读的。

一切都跑在本地。除非配了视觉端点 —— 而且只发需要它的页面 —— 否则不向任何地方上传。

## 评测

`docfusion bench --set <dir>` 用一份参照语料给引擎打分 —— 一个 case 一个目录，里面放 `expected.md` 和它对应的源文档。配对用目录而不是文件名约定，因为 `notes.md` 旁边放 `notes.md` 不是配对，是一个文件。

### 两个错误率，不是一个

第一份真实语料就证明了：把输出和参照当成一个有序字符串来比，会把两种不同的失败混成一团。一个按行识别的引擎拿到三栏报纸，会**横着读**而不是竖着读：它找回了参照里 97.7% 的字符，字符错误率却是 **0.978**。把它读成"引擎坏了"，这个数字是错的；读成"这个引擎排不了一页的顺序"，它是对的，而且可以据此行动。

所以 `Score` 两个都报：

- `character_error_rate` —— 含阅读顺序。读者实际体验到的东西。
- `content_error_rate` —— 同样的字符，不计顺序。活下来的东西。

**两者的差就是顺序造成的破坏**，当一页读起来不错但分数很差时，这是第一个该看的地方。

### 基线

24 页，两个引擎跑同一份语料：

| | 本地 RapidOCR | 视觉端点（DeepSeek-V4.1-Flash） |
|---|---|---|
| 平均误差，按阅读顺序 | 0.466 | **0.245** |
| 平均误差，不计顺序 | 0.203 | **0.171** |
| 找到的标题 | 0 / 64 | **9 / 64** |
| 形状正确的表格 | 0 / 9 | **7 / 9** |

**字符上接近，结构上不接近。** 一个按行识别的引擎没有标题和表格的概念。用版面模型来读表格之后，最后那一行从 9 张里对 1 张变成对 7 张 —— 这是整个项目里最大的一次质量提升，而它来自跑一个模型，不是来自调参。

两个引擎还**在不同的页面上失败**，这正是需要两个的全部理由。在一页中文报纸上，本地引擎找回了参照中 97.7% 的字符，而云端模型只找回 72.8%，干净利落地漏掉了报头、编辑和电话号码 —— 因为那个服务商在读之前会把 2754×3939 的扫描件缩到大约 900×1280，小字活不下来。本地引擎跑全分辨率，不在乎这个。

### 语料

第一份语料是**从 OmniDocBench v1.6 的基础子集采样的 24 页**。v1.6 是当前的数据集版本；它内部把基础子集标成 `v1.5` —— 那是**子集的名字，不是版本号**，语料的构建脚本正是按 `subset == "v1.5"` 筛的。`equation_hard`、`layout_hard` 和 `table_hard` 三个子集被刻意排除：它们在设计上就是对抗性的，对普通文档说明不了什么。

三条已知限制，**不做修正**，因为修正等于把它们藏起来：

1. **参照是我们自己生成的。** OmniDocBench 提供的是分区标注，不是 Markdown，所以那些 `expected.md` 是由一个转换器生成的，而它的规则决定了什么算"读对了"。它是靠把页面和参照摆在一起看过才验证的。但它仍然是个转换器。
2. **公式是被污染的。** 参照里带着数据集自己那套 LaTeX，写成 `0 . 1 6 6 \%` 这样带空格的，没有任何引擎会复现这种写法。24 个 case 里有 14 个含 LaTeX，而它们正是分数最差的那些。
3. **页面是电子版渲染成图的。** 没有倾斜、没有相机噪声、没有不均的光照 —— 所以上面每个数字对真实扫描件都是偏乐观的。

> **语料不在这个仓库里。** 真实文档往往涉密，这一份则是数据集的。语料按路径引用（`docfusion bench --set <dir>`），本仓库提供的是工具和打分，不是数据本身。

## 工程笔记

有些事不止做了一遍才做对，记在这里，因为**原因**才是有意思的部分。

**Windows 上的文件替换不是 `rename`。** 覆盖一个已存在的文件需要 `ReplaceFileW`/`MoveFileExW`；普通 rename 会失败或者把目标弄丢。存储层每一次写入都走那条唯一做对了的原子路径。

**打分器看不见代码块里面。** 一个视觉模型会把整页裹进一个围栏代码块，前面加一句"这是本页的转写……"。放着不管，一页就变成一个逐字代码块，所有标题和表格全丢 —— 而且因为围栏里是字面量而不是文本节点，打分器会把一页**转写正确**的内容读成内容错误率 **1.000**。解开那个信封、并教会打分器往围栏里面看之后，两个 case 从 1.000 变成 0.089，语料均值从 0.292 变成 0.245。两个 bug 都是在真实文档上跑出来的，不是测出来的。

**"关掉思考"必须明确要求。** 服务商的默认是开着高强度的思考，而它支配了输出：让它回答一个词，模型在 26 个输出 token 里花了 24 个去思考。它还会让 `temperature` 失去意义 —— 而那是防止模型把一页本该转写的内容改写成别的话的设置。

**GPU 是先量过才信的。** DirectML 执行提供者实现了但默认关闭，因为在真实页面上它们大多没帮上忙：代价在流水线里，不在算术里。

**一个区域里出来两个标题。** 一个标题区域里合法地可以同时有主标题和副标题；一个区域出一个标题会丢掉一个，一行出一个标题则会在一处折行的地方凭空造出一个标题。这条规则被写下来并测过，而不是靠眼睛调出来的。

**这个项目自己也有一个知识库。** `docs/llmwiki/` 把设计记成一份活文档，每件事一份任务文档、每个任务带一个验证步骤，外加一份只追加的变更记录，每一条都说明改了什么**以及为什么** —— 包括那些改变了决定的实测数字。

## 仓库结构

```
DocFusion/
  crates/
    docfusion-core/     IR、抽取器、引擎、校验、渲染、导出
    docfusion-store/    清单、内容寻址、缓存、配置、对账
    docfusion-cli/      `docfusion` 命令
    docfusion-gui/      Tauri 窗口（Rust 后端 + 静态 `ui/`）
  docs/
    setup.md            安装指南，作为产品交付物
    llmwiki/            design.md、changelog.md、tasks/
```

拆成多个 crate 而不是用特性开关，是刻意的：**命令行不该编译 Tauri。** Tauri 的依赖树有几百个 crate，一个只用命令行的人不该为它付构建时间的账。这也让 `docfusion-core` 可以脱离用户界面单测，对着黄金 IR 语料而不是穿过一个 UI 来验证。

## 构建与测试

```bash
cargo build --release                  # 命令行
cargo run --release -p docfusion-gui   # 窗口
cargo test --workspace                 # 603 个测试
cargo clippy --workspace --all-targets
```

首次构建需要联网：`pdfium-bundled` 会下载并链接 Chromium 的 PDF 引擎，`ort` 会取 ONNX Runtime。两者都不需要你在机器上预装任何东西。

CI 在 Windows 上跑 clippy 和测试，在 Linux 和 macOS 上构建那三个可移植的 crate。**格式检查不在门禁里** —— 这棵代码树早于 `rustfmt` 对它发表意见的时候，而一个横跨 34 个文件的空白改动，埋掉的历史比它清理掉的多。

### 平台

**Windows 是构建和发布的目标平台。** Linux 和 macOS 能构建，两个原生依赖也都为它们提供二进制，所以流水线本身并不依赖 Windows。但从头到尾没发生过的事，是有人在 Windows 之外**运行过那个窗口** —— 所以 CI 里那个 canary 刻意排除了它，而不是在一个没人验证过的东西旁边挂一个绿色对勾。

离"在别处发布"还差两件事。macOS 需要签名和公证，否则 Gatekeeper 会直接拒绝这个下载；而 Intel macOS 根本构建不了：ONNX Runtime 没有 `x86_64-apple-darwin` 的二进制，微软也没有。

### 发布产物

打一个 `v*` tag 会产生两样东西：

| | |
|---|---|
| `docfusion-<tag>-windows-x86_64.zip` | 命令行，免安装，附 `README.md`、`LICENSE`、`THIRD-PARTY.md` |
| `DocFusion_<version>_x64-setup.exe` | 窗口的 NSIS 安装器，按用户安装，不需要管理员 |

这些二进制**没有代码签名**，所以首次运行时 SmartScreen 会告警。模型权重不在任何一个产物里 —— 144 MB 是第一次用到时才取的。

**卸载时会问要不要一并清理**，而且是分**两个**问题问，因为它们是两种量级的决定：一个是模型和配置，另一个是那个装着已转换文档的库，后者**默认为「否」**。库如果放在默认位置以外，卸载器找不到，也不会去碰。见[卸载](docs/setup.md#10-uninstalling)。
